# Contributing

Thank you for looking at this work critically. The project's aim is to be as open as possible about what was done and how far it can be checked, so that weak points are found and fixed. A reproduction attempt, a corrected pattern, a question about a source's terms or a report that a claim is not supported all count as contributions.

This repository holds two linked projects: the court-decision dataset and its tools (repository root) and an AI-assisted systematic review ([`legal-last-mile-systematic-review/`](legal-last-mile-systematic-review/START_HERE.md)). The review has stricter rules of its own (below).

## Ways to contribute

| You want to | Do this |
|---|---|
| Report that a number, claim or file is wrong | Open an issue; give the file and line and say how you checked. The template `.github/ISSUE_TEMPLATE/audit-report.yml` suits reproduction results and weaknesses |
| Test a documented weakness | Pick an ID from `legal-last-mile-systematic-review/00_admin/WEAKNESSES.md` or `docs/findings-register.csv`, run the test described, report the result with the ID |
| Fix a bug in a scraper, the merge step or the coding engine | Open an issue first if the change could alter what is collected or how a decision is classified (see "Changes that need the researcher's approval") |
| Add a test | Add it under `tests/` (see below) |
| Improve documentation | Edit the Markdown; keep statements to what the repository shows |
| Report a security or privacy problem | Follow [`SECURITY.md`](SECURITY.md), not a public issue |

## Before you open a pull request

1. Run the offline tests from the repository root: `python3 -m unittest discover -s tests -v`. They need no network and no secrets. Documented defects appear as *expected failures*; if you fix one, the test will report an "unexpected success": remove its `@unittest.expectedFailure` marker in the same pull request.
2. If you touch `legal-last-mile-systematic-review/`, run `python3 code/analysis/verify_repository.py` there (and `bash code/analysis/regenerate_all.sh` if you changed a generator or data file).
3. Keep Python 3.8 compatibility (`requires-python >= 3.8`).
4. Do not commit credentials, personal data, licensed full texts or large data files. `tests/test_repository_hygiene.py` scans code, configuration and documents for common credential patterns; it does not scan data files, so check those yourself.
5. State in the pull request description what you ran and what you did not.

## Rules for scrapers and network code

- **No live requests in tests.** Test parsing with fixed synthetic strings (see `tests/test_offline_helpers.py`).
- Identify the client honestly: project name, repository URL and a monitored contact address in the User-Agent. Do not imitate a browser.
- Do not disable TLS verification.
- Respect each source's terms and rate limits ([`docs/source-register.md`](docs/source-register.md)). Do not circumvent CAPTCHAs, logins or blocks.
- Take paths and keys from environment variables documented in `.env.example`; never hard-code a personal path or a key.

## Changes that need the researcher's approval

A change that could alter research results, the scope of collection, source selection, the legal interpretation encoded in the classification rules, or a historical record must not be merged silently. Explain in the pull request what changes, on what data you checked it, and how the effect can be measured. Examples: correcting the win/loss patterns (changes coded outcomes), changing a scraper's filter or User-Agent (can change what a server returns), editing a data file.

## Using AI tools

AI assistance is welcome and must be disclosed. In the pull request say which tool and model you used and for what, and confirm that you read and ran the result. Do not paste unpublished material, licensed full texts or personal data into an external AI service. The project's own AI use is described in [`docs/ai-use-and-disclosure.md`](docs/ai-use-and-disclosure.md).

## Rules specific to the systematic review

- Human verification is counted strictly. No `CK` confirmation (the principal investigator's initials) is ever recorded unless the researcher reviewed the evidence and instructed it. Contributors do not enter `CK`.
- An AI re-check is recorded as "AI-checked", never as a human confirmation.
- Generated files (`STUDY_AUDIT_TRAIL`, `AI_USE_LEDGER`, `WEAKNESS_REGISTER`, `DATA_MANIFEST`, the atlas, `CURRENT_FIGURES.md`) are regenerated by their scripts, not edited by hand; the verifier fails if they are stale. To add a weakness, edit `code/analysis/weakness_register_source.csv`.
- Deviations from the protocol and errors found are added to `00_admin/DEVIATIONS_REGISTER.csv` and `00_admin/ERRORS_FOUND_REGISTER.csv` with a date.

## Licence of contributions

The licences stated in this repository are not consistent across components (see finding F-18 in [`docs/audit-report.md`](docs/audit-report.md)). Until that is settled, assume your contribution is offered under the licence file in the folder you change (MIT for the root and the review folder; AGPL-3.0 is stated for `research-assistant/`) and ask if unsure.

## Conduct

Be specific, be kind, assume good faith. A found weakness is a finding, not an accusation.
